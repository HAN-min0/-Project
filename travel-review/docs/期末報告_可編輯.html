平價旅遊評價系統之設計與實作　個人本機版

摘要

本專題以個人規劃臺灣輕旅行的需求為出發點，設計可操作的旅遊評價網站。系統先將景點分成北部、中部、南部及東部，再提供交通便利、好停車、風景好看與花費較低等條件，協助使用者縮小選項。景點詳情包含介紹、特色、缺點、六項細分評價、每人花費與個人心得；文字心得可不填寫，仍可保存評分。

最終版本採 React 與 TypeScript 製作前端，以 Vite 建置；後端使用 Node.js 原生 HTTP 模組及 node:sqlite，將資料寫入專案內的 data/travel.sqlite。GitHub 用於原始碼保存與版本管理，實際資料留在執行電腦。系統不需要 Sites 或雲端資料庫，適合下載後在本機使用。

初始內容包含 42 個景點、18 筆公開平台整體評分快照及 22 則少量心得改寫，另有預設關閉的 72 則虛構示範資料。網路整體星等與個人細項分數分開處理，沒有分數或花費時不當成零。個人版在每個景點只保留一筆個人評價，不能把這些分數解讀成多位真實旅客的調查。

功能驗證完成 26 項自動測試與 12 項瀏覽器操作檢查，涵蓋 SQLite 保存、新增景點、空白心得、條件篩選、比較及匯出。LLM 摘要接口已保留，但交付時未設定 API 金鑰，未進行實際模型效果驗證。

壹 研究背景與動機

1 1 研究背景

旅遊規劃常需要同時考量地區、移動方式、停車、景觀及支出。整體星等雖方便瀏覽，但未必能回答「停車是否符合我的需求」或「這次出遊是否能控制花費」。不同平台的評分也有不同樣本，直接混成一個平均值，容易讓使用者失去判斷依據。

本專題的使用情境是個人在自己的電腦整理旅遊資訊，透過公開評價參考與自己的評分，累積可回查的景點名單。程式預計以 GitHub 保存，執行時由本機後端連接 SQLite。此方式能讓資料庫位置、程式流程與資料內容在課堂上清楚展示。

1 2 研究動機

第一，景點應先有明確的地區分類，使用者不必從全部名單逐一尋找。第二，將整體感受拆成交通、停車、整潔、設施、附近攤販與風景，可讓比較更貼近實際需求。第三，不是每次到訪都有完整心得，因此文字應為選填，並允許尚未體驗的細項保留空值。

第四，固定的程式名單無法涵蓋個人新發現的地方，因此需要新增景點與資料庫保存功能。重新整理或關閉程式後，景點和評價仍應存在；換電腦時則透過資料庫備份或 JSON 移轉，而非期待 GitHub 自動同步個人資料。

1 3 研究目的與範圍

貳 文獻探討

2 1 群眾資訊與評價參考

Lorenz、Rauhut、Schweitzer 與 Helbing（2011）指出，在其群體估計實驗中，社會影響可能使意見差異縮小，卻不一定改善整體準確度 [1]。這提供本專題一個設計啟發：除了呈現平均值，也應保留來源與不同意見，避免把單一高分當成品質保證。該研究不是旅遊網站實驗，因此不能直接用來證明本系統的推薦有效。

本系統參考公開旅遊平台與旅遊作者的資訊，並保留短篇改寫和原始連結。這些資訊可視為外部經驗的整理，但目前只是少量便利取樣，不能宣稱涵蓋所有旅客意見。個人版自己的評分也只有一位操作者，與多人群體投票有本質差異。

2 2 前後端分工

React 以元件組合介面，適合將景點卡片、分區、篩選器和表單拆開管理 [2]。TypeScript 則用型別描述景點、評價與可空值欄位，讓前端計算分數時能清楚區分數字與沒有資料 [3]。Vite 提供開發伺服器與建置工具，將前端輸出為瀏覽器使用的檔案 [4]。

2 3 SQLite 與本機資料保存

Node.js 的 node:sqlite 提供 DatabaseSync，可開啟檔案型或記憶體型資料庫，並以預備陳述式綁定參數 [5]。本專題使用檔案型 SQLite 儲存實際資料，記憶體型資料庫則用於部分自動測試。SQLite STRICT 表格能限制欄位型別，本系統再以 CHECK、UNIQUE 與外鍵補上資料規則 [6]。

2 4 原始碼平台與執行環境

GitHub 可用於保存及管理程式碼；GitHub Pages 的官方定位則是提供 HTML、CSS 與 JavaScript 等靜態網站內容 [7]。本系統包含可寫入 SQLite 的 Node.js 後端，因此本次使用方式是從倉庫下載後在電腦啟動，不能只將資料夾放上 GitHub Pages 就得到同樣的資料庫功能。

2 5 LLM 摘要的定位

本專題保留可選用的 Responses API 摘要接口 [8]，但目前只驗證未設定金鑰時的規則統計。模型摘要需另行設定並測試；研究成果不將程式中存在的接口視為已完成的 AI 效果實驗。

3 3 資料庫寫在哪裡

實際資料庫是專案根目錄下的 data/travel.sqlite。第一次啟動時，後端自動建立檔案與資料表，接著匯入初始景點及來源快照。此檔案會保存之後新增的景點、評分及選填文字，重新整理頁面或重新啟動程式都不會重新清空。

例如專案解壓縮到 D:\travel-review，資料庫就位於 D:\travel-review\data\travel.sqlite。程式用自身所在的專案位置組合路徑，因此不會因終端機從別的資料夾啟動，就意外建立在另一個工作目錄。

import { DatabaseSync } from 'node:sqlite';

GitHub 裡的原始碼可以重建系統及初始資料；正在使用的 travel.sqlite 保存個人新增內容；另外匯出的初始 SQLite 範例則只含 42 個景點與來源資料，沒有個人評價。換電腦時，應移轉實際資料庫或匯入自己的 JSON，不能只依賴初始範例檔。

文字心得未填時，後端寫入空字串 ""，仍保存有效的整體評分。細項沒有體驗或金額不確定時使用 NULL；0 元則是已明確填寫的免費支出。兩者在統計時有不同意義。

新增的 24 個內建景點沒有已查核網路星等時會顯示沒有，使用者自行新增的景點也不會自動產生分數。這能避免為了讓畫面完整而填入虛構評價。

3 8 推薦與統計規則

有效值與平均花費

各細項平均只使用有效數字，NULL 不參與分母。花費採有效填報金額的算術平均，包含明確填寫的 0 元；沒有金額則排除。支出範圍限定為單次到訪的每人餐飲、活動及購物，不含往返交通與住宿。

平均花費 = 有效填報金額總和 / 有效金額筆數

例如有效金額為 100、100、1000 元，平均為 400 元；若另有一筆沒有填寫金額，平均仍是 400 元，而不是將空值當作零後算成 300 元。免費入場也不等於該次所有花費一定為零。

多條件交集

條件判斷規則
好停車個人／目前選用資料的停車平均至少 4 分
交通便利交通平均至少 4 分
風景好看風景平均至少 4 分
花費較低有效平均花費不超過使用者設定的上限

多個條件必須全部符合。缺少該項分數的景點不通過該項條件，使用者可先取消條件瀏覽。金額上限只在勾選花費較低時套用，網路整體星等不換算成停車或交通分數。

調整分數的用途與限制

B = (n × R + 5 × C) / (n + 5)

R 為景點整體平均、n 為目前選用的評價筆數、C 為全站選用評價平均。這個簡單平滑公式用於展示排序，參數 5 是原型設計選擇，未以真實旅客資料調校。無評價時不顯示分數。

個人版每景點只有一筆自己的評價，關閉示範時平均通常就是自己的填答。此時調整分數沒有多人樣本的解釋力，應優先依個人需求與來源內容判斷，不能當成群眾信任度或統計驗證結果。

肆 結論與展望

4 1 結論

本專題完成可在個人電腦執行的旅遊評價系統，將地區瀏覽、條件推薦、景點新增、六項評分與選填心得整合在同一介面。資料庫固定保存於 data/travel.sqlite，程式以 Node.js 的預備陳述式讀寫，讓使用者能清楚知道資料寫在哪裡，以及重新啟動後為何仍能保留。

在資料呈現上，系統將網路星等、心得改寫與個人評價分開，保留來源及查核日期，也區分沒有資料與零元花費。這些設計有助於使用者理解推薦依據；但本次功能測試只能證明指定操作能完成，不能直接證明旅遊決策品質已提升。

4 2 目前限制

第一，網路資料為人工核對的少量快照，內容可能隨時間變動，且未涵蓋所有景點。第二，個人評價不具多人樣本代表性，平滑分數只作展示參考。第三，資料留在本機，換電腦時需要自行移轉，不會因 GitHub 倉庫更新而同步。

第四，本版沒有多人登入及管理者審核機制，只適合個人本機使用。第五，AI 摘要尚未完成模型實測，仍需測量摘要是否支持原始評論、是否保留不同意見，以及是否正確處理空白心得與示範資料。

4 3 後續發展

後續可先讓實際使用者完成「找景點、新增景點、只填分數、比較選項」等任務，紀錄完成率、操作時間與理解困難，並詢問使用者能否分辨來源星等和個人細項評分。取得足夠且有同意的樣本後，再評估篩選與排序是否符合需求。

資料方面可增加正式授權的更新來源、查核流程與版本記錄；若改為多人線上服務，則需另行設計帳號、資料權限、內容管理及持久化主機。上述屬未來規劃，本次沒有將它們描述成已完成功能。
